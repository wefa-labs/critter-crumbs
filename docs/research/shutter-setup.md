# Shutter setup and a read-only deployment preflight

Checked 2026-09-06 03:03 UTC (2026-09-05 locally). **Chiado can be configured without an account or API key. Mainnet offers anonymous access, but Critter Crumbs must keep live mainnet registration blocked: the API's current eon key still disagrees with the deployment named in its README.** A Shutter setup script should configure and verify the existing service; it should not deploy a project registry contract.

## Which guide to follow

The user's [Get Started guide](https://docs.shutter.network/docs/protocol/api/get_started) explicitly redirects readers to the API README as the current reference. Its examples have stale root paths, no response envelope, a parameter GET missing the required registrant address, and an SDK encryption call with the wrong argument order for our pinned SDK. Its event-trigger examples also do not represent the time-based interface used by this project. Follow the [API README](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/README.md), [router](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/internal/router/router.go) and [pinned SDK source](https://github.com/shutter-network/shutter-sdk/blob/9a01a6e2b25dd310f736673ed7e4407199386dcc/src/crypto/crypto.ts). Fresh GitHub API lookup confirmed the upstream main revision remains `a1755713419611ae2743e8c7cb7f6e69c86681f2`; this is the same revision already investigated in V2/V3.

The relevant service routes, for either origin, are:

| Operation | Exact route | Important shape |
|---|---|---|
| Read parameters | `GET /api/time/get_data_for_encryption?address=<registrant>&identityPrefix=<bytes32>` | `{ message: { eon, identity, identity_prefix, eon_key, epoch_id } }` |
| Register one feast; writes on chain | `POST /api/time/register_identity` | Body `{ decryptionTimestamp: integerSeconds, identityPrefix: bytes32 }`; response `{ message: { eon, identity, identity_prefix, eon_key, tx_hash } }` |
| Read released key | `GET /api/time/get_decryption_key?identity=<bytes32>` | A before-release error is distinct from an unregistered identity |
| Check a mainnet bearer key | `GET /check_authentication` | Require JSON `result === 'authenticated'`; HTTP 200 alone is insufficient |

The API's encryption call uses the supplied address to calculate an identity; it does not certify that address as its active signer. The SDK call is `encryptData(messageHex, identityHex, eonKeyHex, sigmaHex)`, using the returned 32-byte identity as the preimage. [Handlers](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/internal/service/crypto.go), [identity calculation](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/common/utils.go), [SDK source](https://github.com/shutter-network/shutter-sdk/blob/9a01a6e2b25dd310f736673ed7e4407199386dcc/src/crypto/crypto.ts)

## Practical account/key setup

For a Chiado rehearsal, choose `SHUTTER_MODE=chiado`, set `SHUTTER_API_BASE=https://shutter-api.chiado.staging.shutter.network`, use the verified deployment inputs below, and leave `SHUTTER_API_KEY` empty. The upstream documentation says Chiado has no rate limit. Anonymous parameter retrieval was observed successfully; this research did not create a new registration or prove a new complete release lifecycle. [Access documentation](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/README.md#rate-limits--authorization)

For mainnet, the documented higher-limit-key process is a human request to `loring@brainbot.com`. No self-service signup portal, account-creation API, or published paid-plan checkout is documented in the inspected guide/README. Afolabi should request the intended Standard key and ask the operator to confirm commercial terms, registration gas coverage, and the actual mainnet RPC chain, registry, key-broadcast contract and API registrant. The deployment mismatch makes those last details necessary. No message was sent and no account was created. [Key provisioning instructions](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/README.md#rate-limits--authorization)

The rate policy grants anonymous mainnet requests 5 registrations, 10 parameter reads and 20 key reads per IP/day. Standard grants 500/1,000/2,000 per key/day; Premium grants 2,500/5,000/10,000. An unrecognized bearer value falls into the anonymous matcher, so a successful parameter response does not validate a key. The API signer's account pays registration gas; clients do not supply a Gnosis signing key for the API route. [Exact rate policy](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/apikeys/limits.yaml), [key matcher](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/apikeys/apikeys.py), [registration implementation](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/internal/usecase/crypto.go)

After the operator supplies a key, the human stores it in the ignored local environment or Vercel's server-only `SHUTTER_API_KEY`. The preflight can read it from the environment and send `Authorization: Bearer <key>` to the configured Shutter origin's authentication GET, without printing headers, key values or credential-bearing redirect requests. A valid response body must be `{"result":"authenticated"}`. The source accepts both `/check_authentication` and `/api/check_authentication`; it is Caddy middleware, not a Go API handler. A Chiado 404 is not a failure when that mode intentionally uses anonymous access. No valid key was supplied or tested here. [Authentication middleware](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/docker-compose.rate_limit.yaml)

T14's initial assumption that the project needs to register for a Shutter key is therefore a project ownership/operations choice, not a prerequisite for anonymous Chiado or anonymous mainnet reads. Preserve the human-owned Standard-key/terms follow-up instead of creating an account in code or assuming a paid plan exists. The API key identifies a rate-limit customer; it is not the chain signing key, does not make Afolabi the registrant, and does not resolve a deployment/key mismatch. These are proposed decision clarifications, not changes to the accepted project policy.

## Exact preflight that makes no chain write

The current `.env.example` already names `SHUTTER_MODE`, `SHUTTER_API_BASE`, `SHUTTER_API_KEY`, `SHUTTER_RPC_URL`, `SHUTTER_REGISTRY_ADDRESS`, `SHUTTER_KEY_BROADCAST_ADDRESS`, and `SHUTTER_REGISTRANT_ADDRESS`. Expected chain ID can be fixed by mode. The following checks can run in one short script using existing viem and fetch; they need no new dependency or private signing key.

| Check | Read-only operation and pass condition |
|---|---|
| Configuration | Parse mode, expected origin and nonzero contract/registrant addresses. Never silently mix Chiado and mainnet. Redact secrets from reports. |
| Chain | `eth_chainId`; exactly 10200 for Chiado or 100 for Gnosis mainnet. This is separate from Base's EAS chain. |
| Finalized anchor | `eth_getBlockByNumber('finalized', false)`; save number/hash and use that explicit number for related getters. Unsupported finality or RPC errors are inconclusive, not ready. |
| Deployed contracts | `eth_getCode(registry, block)` and `eth_getCode(keyBroadcast, block)` must return nonempty code. Code presence alone does not prove the API uses those contracts. |
| Optional bearer validation | If a mainnet key was supplied, call the authentication GET and inspect the JSON result. No key means explicit anonymous mode; do not claim credential validation. |
| Parameter shape | Make one GET with a public nonzero probe prefix, such as `0x` followed by `11` 32 times, and the configured registrant. Check the message envelope, uint64 eon, 32-byte prefix/identity, observed 96-byte eon-key encoding, and 48-byte epoch ID. The prefix is a read probe, never a feast registration prefix. |
| Identity | Locally compute `keccak256(rawPrefixBytes32 || rawRegistrantAddressBytes20)` and match `message.identity`. This confirms derivation for the configured address, not the active API signer's ownership. |
| Eon key | `eth_call` to `getEonKey(uint64 eon)` at the finalized anchor; decode dynamic bytes and compare exactly with the API's public key. Empty/unfinalized or mismatching data means not ready. At a genuine eon transition, refresh the finalized anchor and recheck once; do not replace persisted feast keys with current parameters. |
| Registry interface | `registrations(bytes32 identity)` returns `(uint64 eon,uint64 timestamp)`. A probe's zero timestamp means unregistered at that block. It proves neither future registration success nor anything about the pending pool. |
| Optional known-attempt recovery | For an existing attempt, read its identity, require the original deadline, read its stored eon's key, and match `IdentityRegistered` logs/receipt against the persisted deployment, prefix and registrant. Use bounded log pages. Never invoke registration as a health check. |

The getter selectors are `getEonKey(uint64) = 0x8a0b8b28` and `registrations(bytes32) = 0xda7c6a42`. The registry event is `IdentityRegistered(uint64 eon,bytes32 identityPrefix,address sender,uint64 timestamp)`; none of its parameters are indexed. Topic0 is `0xa254e5a8078a79959db8c7203cbd84a28d6e1b9750d0c4fd743a1a069c21b05b`. Filter by address/topic and decode/filter arguments locally. A successful historical event from the documented API address supplies evidence about that past transaction; neither it nor a parameter GET proves that the service's current private configuration has not rotated. [Registry source](https://github.com/shutter-network/contracts/blob/7e53b1579b04de3030e30065699540964d95e603/src/shutter-service/ShutterRegistry.sol), [key-broadcast source](https://github.com/shutter-network/contracts/blob/7e53b1579b04de3030e30065699540964d95e603/src/common/KeyBroadcastContract.sol)

A stronger optional current-eon check can use the operator-confirmed keyper-set manager's `getKeyperSetIndexByBlock(uint64 blockNumber) returns (uint64)`. The API uses this method with its current head. The published Chiado manager is `0xEf2F473f64C11e1CF234D75947643e76f7CD115D`. This adds deployment metadata and a head/finality race; it is not required to recover an older registered eon. Do not infer an active mainnet manager from unrelated deployment assets. [API eon selection](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/internal/usecase/crypto.go), [published Chiado assets](https://github.com/shutter-network/shutter-keyper-assets/blob/300713e8f8a54807df639523cb56ff81d67ef556/shutter-api-chiado-102000/variables.env)

## Safe deployment-script semantics

The proposed script should default to a **read-only preflight**: report configuration, chain/deployment evidence, authentication state and key consistency; fail with a useful reason if the checks are incomplete. It may emit a redacted setup checklist, but must not create a schema, contract, account, identity or feast and must not treat an API GET as a registration. A command labelled “deploy Shutter” would misdescribe this v0 integration.

Opening an actual feast is a separate, explicitly authorized operation through the existing authenticated creator route `POST /api/feasts/:id/open`. That route calls the existing Timelock registration/recovery adapter. It persists the original prefix, deadline and deployment before the POST, confirms the chain registration and original eon key, and only then opens gathering. Retrying must use the same attempt; a lost POST response is not proof that nothing was sent. The setup script should not duplicate that workflow with a fresh prefix or bypass its transaction/state rules. [Registration and request-cancellation behavior](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/internal/usecase/crypto.go)

Shutter's registry and keypers already exist. Deploying another project registry would not automatically make those keypers monitor it and would change the approved integration. Direct self-registration through the existing registry is a different funded-signer design with a different identity derivation address. EAS schema registration on Base/Base Sepolia is also a separate explicit chain write, unrelated to Shutter setup. None belongs in this read-only command. [Service architecture](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/README.md#overview), [API versus self-registration](https://github.com/shutter-network/shutter-api/blob/a1755713419611ae2743e8c7cb7f6e69c86681f2/README.md#1a-register-an-identity-with-time-based-decryption-triggers)
