# Vercel Node functions and npm workspaces

Checked 2026-09-04 for Phase 1 verification item 2.

**Verified choice:** keep `api/` at the repository root and expose built JavaScript from `@critter-crumbs/shared` and `@critter-crumbs/core`. With `@vercel/node@12.0.1`, built exports resolve through preserved npm workspace links in an independently materialized function output. TypeScript source exports fail there because the emitted JavaScript paths no longer match their exports. Build shared before core, then the app. This preserves the workspace seams specified in [the foundation layout](../foundation/README.md).

## Evidence

npm installs configured workspaces as links in the root `node_modules`, allowing imports by package name. This is npm's documented workspace behavior and does not require TypeScript path aliases. [npm workspace documentation](https://docs.npmjs.com/cli/v10/using-npm/workspaces/)

Vercel's Node runtime compiles TypeScript functions under the project's root `api/`. Its documentation excludes TypeScript path mappings and project references from supported compiler configuration. Set the eventual Vercel project root to the repository root; `packages/app` remains the Vite root. [Vercel Node runtime documentation](https://vercel.com/docs/functions/runtimes/node-js)

Vercel's file tracer supports package `exports` and the `node`, `import`, `require`, and `default` conditions. Its resolver follows package exports and resolves real paths, which provides source evidence for following npm workspace links. [File tracer documentation](https://github.com/vercel/nft#exports--imports), [resolver source](https://github.com/vercel/nft/blob/main/src/resolve-dependency.ts)

The Node builder calls that tracer with TypeScript enabled and compiles traced TypeScript through its `readFile` hook. It then stores compiled files at renamed JavaScript paths without rewriting a package's TypeScript `exports` target. The experiment below confirms the resulting failure for `./src/index.ts`. [Node builder source: `compile`, `compileTypeScript`, `renameTStoJS`, and `preparedFiles`](https://github.com/vercel/vercel/blob/main/packages/node/src/build.ts)

For generated dependencies, Vercel documents a `vercel-build` script in the function's nearest ancestor `package.json`. A root script can therefore build shared and core before function tracing. [Vercel custom Node build step](https://vercel.com/docs/functions/runtimes/node-js/advanced-node-configuration#custom-build-step-for-node.js)

## Selected package interface

Use this shape for shared and core, with ESM JavaScript and declarations generated by TypeScript:

```json
{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    }
  }
}
```

The build order is `shared → core → app`. Root function files import package names. No wildcard export or compiler path alias is needed.

## Observed bundler test

The experiment used Node `v22.22.1`, npm `11.19.1`, `@vercel/node@12.0.1`, `@vercel/build-utils@14.9.1`, and `@vercel/nft@1.10.0`. It inspected the installed builder's `downloadInstallAndBundle` and `build` implementations before invoking them.

Each temporary fixture has a root `api/probe.ts` importing core, with core importing shared. The only behavior is returning the marker `core:shared`. An offline npm install creates real workspace links for the two synthetic packages; it fetches no external dependency and runs no lifecycle script. For the dist shape, TypeScript builds shared and then core before the Node builder runs.

The Node builder receives `files`, `entrypoint: 'api/probe.ts'`, `workPath`, `repoRootPath`, `config: { projectSettings: { installCommand: '' } }`, `considerBuildCommand: true`, and `meta: { skipDownload: true }`. The fixture declares no build script. Both builder invocations print `Skipping "install" command...`. The file references already point to materialized inputs; skipping their download does not skip tracing or compilation.

The experiment materializes the returned function files with Vercel's own `download` helper, preserving symlinks. It checks that both output links resolve inside the independent output directory, then starts a fresh Node process there to import and invoke `api/probe.js`. Thus the passing dist invocation cannot borrow the original workspace sources or repository dependencies.

Repeat the portable experiment from the repository root:

```sh
npm run check:workspaces
```

The original experiment asserted source failure and dist success. The retained script requires dist success and reports the source result. Its generated fixtures stay in the OS temporary directory; it creates no production function, Vercel project, link, or deployment. This proves local function packaging and emitted module resolution, not deployment routing or future domain imports.
