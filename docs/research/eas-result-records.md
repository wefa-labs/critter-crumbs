# EAS result records

Observed 2026-09-05 against EAS SDK 2.10.0 and contracts 1.7.1. A read-only Base RPC scan captured an existing unrelated attestation, receipt, transaction, finalized header, schema and getter responses in `packages/core/test/fixtures/eas-base-record.json`. No transaction was sent. Result-schema variants are explicitly synthetic; the captured attestation is not a Critter Crumbs result.

`Attested(address indexed recipient,address indexed attester,bytes32 uid,bytes32 indexed schemaUID)` puts the UID in log data, with recipient, attester and schema in topics. `getAttestation` returns UID, schema, time, expiration time, revocation time, reference UID, recipient, attester, revocable and data. Check those stored fields: `isAttestationValid` only establishes existence. The SDK defaults `revocable` to true, so prepared result transactions explicitly set false. [EAS contract source](https://github.com/ethereum-attestation-service/eas-contracts/blob/v1.7.1/contracts/EAS.sol), [SDK source](https://github.com/ethereum-attestation-service/eas-sdk/tree/v2.10.0).

The captured receipt UID agrees with the SDK's receipt helper. Ethers and viem decode the getter identically; transaction calldata, event and stored attestation agree. The captured schema UID also agrees with the SDK registry calculation. These checks are rerun offline from the fixture. Base and Base Sepolia use EAS `0x4200000000000000000000000000000000000021` and SchemaRegistry `0x4200000000000000000000000000000000000020`. [Base EAS documentation](https://docs.base.org/base-chain/network-information/base-contracts).

Runtime verification uses a configured RPC on chain 8453 or 84532, a successful finalized receipt and a matching event from the configured EAS contract. It reads the stored attestation at the receipt block and binds the decoded result to the feast's immutable metadata. It verifies provenance and structural consistency, not the member's tally. No allocation enters a handler.
