# Critter identity, storage, and optional public provenance

Investigated 15 October 2026 for the QA plan. This is a proposal, not an adopted decision. Implementation references below use commit `b908f4a78f819bee829c5b0a3a761f848f7ad111`, read from `/Users/afo/.codex/worktrees/dusk-prefetch/critter-crumbs`. The parent investigation matched that build to the deployed frontend. Server environment and deployed database contents were not inspected; the frontend match does not prove their configuration.

## What exists today

**Creating a burrow makes a database record, with no blockchain transaction.** The authenticated API generates a UUID and atomically inserts the burrow and its creator's membership. The PostgreSQL tables store the name, creator, creation time, membership, and revision. The production database adapter is Neon. There is no burrow registration contract in this path. [API route](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/api.ts), [store](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/store.ts), [schema](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/db/migrations/0001_init.sql), [database adapter](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/database.ts).

**A person's critter is reconstructed in the browser.** The generator validates and lowercases the address, combines it with a variant (`0`–`4`) and generator version, hashes that text with `cyrb53`, and feeds Mulberry32 to select shape, proportions, features, and colour. Option critters use their deterministic target ID in place of an address. The profile stores address, variant, reroll count, lock, display name, and cached ENS name; it stores neither an image nor the generated parameters. Keeping a critter locks the choice in PostgreSQL; reaching variant 4 also locks it. [Generators](https://github.com/wefa-labs/critter-crumbs/tree/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/core/src/generator), [profile type](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/shared/src/types.ts), [profile updates](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/store.ts).

**Production deliberately renders version 1; development defaults to version 2.** `import.meta.env.DEV` selects v2, unless `?critters=1` requests production parity. Production selects v1, and only v1 supports the 3D mesh. V2 introduces earth, water, fire, and air families. This is a concrete contributor to the difference between design exploration and deployed critters. Generator version is a global build-mode choice, not a field stored with each profile or feast portrait. A future global switch would redraw an existing person's locked variant. [Version selection](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/app/src/portraits/version.ts), [portrait reconstruction](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/app/src/app/ui.tsx), [feast portrait data](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/feasts.ts).

**Deterministic appearance is not immutable identity.** `cyrb53` is a noncryptographic visual seed hash; Mulberry32 uses only its low 32 bits. Collisions and repeated appearances are possible. This does not authenticate an owner, publish a registration, or preserve a renderer after a deployment changes it. Use a cryptographic hash over canonical data for any provenance commitment, while preserving existing generator outputs. [Implementation and independent vectors](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/docs/research/generator-v1-vectors.md), [algorithm author's source](https://github.com/bryc/code/blob/master/jshash/experimental/cyrb53.js).

**ENS input already exists at the API boundary.** Adding a member accepts an address or resolves an ENS name through a server-side Ethereum mainnet client, when configured. Profile display names use reverse lookup with forward verification and a 24-hour cache. The QA work should verify and explain this existing path rather than treat ENS as an entirely new integration. [Member addition](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/burrows.ts), [resolver](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/ens.ts), [profile cache](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/profiles.ts).

## What an architecture explanation should distinguish

| Part | Role and limit |
|---|---|
| Connected account | Proves control of an address and signs data. Critter creation and burrow creation do not require a transaction. |
| PostgreSQL / Neon | Stores profiles, burrow membership, statements, feast metadata, and encrypted scatters. Membership and metadata are known to the server. Statements are plain text in storage, hidden by API phase/access rules until scattering; they are not protected by the scatter encryption. The server does not receive plaintext allocations. |
| EAS | Provides structured signed offchain scatter attestations stored by the app. An offchain attestation does not automatically appear on a blockchain or explorer. |
| Shutter | Registers a feast encryption identity and closing time on Gnosis or Chiado, then supplies the released decryption key. This encryption identity is unrelated to a critter's identity. Clients decrypt and tally locally. |
| Base / Base Sepolia | Hosts the EAS contracts used for an optional public result record. This records numbers; it does not distribute money. |

These roles follow the [technical spec](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/docs/04-technical-spec.md), [scatter persistence](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/ballots.ts), and [Shutter opening path](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/feasts.ts). EAS confirms that offchain attestations can remain privately stored and require no gas. Shutter's current API reference describes registration and threshold key release; its keypers remain a trust assumption. [EAS storage documentation](https://docs.attest.org/docs/tutorials/storing-offchain-data), [Shutter API reference](https://github.com/shutter-network/shutter-api#readme).

**Current build caveat:** injected accounts are configured for chain `84532` (Base Sepolia). The result UI allows its local rehearsal recorder only in development with a rehearsal account; ordinary production accounts are rejected by this UI path. Underlying EAS transaction preparation and receipt verification exist, but this is not evidence of a working production result-recording flow. Shutter mode is selected by server configuration and cannot be inferred from the frontend. The explanation must label test/rehearsal behaviour accurately. [Account setup](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/app/src/app/app.tsx), [result UI](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/app/src/app/result-record.tsx), [server runtime](https://github.com/wefa-labs/critter-crumbs/blob/b908f4a78f819bee829c5b0a3a761f848f7ad111/packages/api/src/runtime.ts), [Base chain IDs](https://docs.base.org/base-chain/api-reference/ethereum-json-rpc-api/eth_chainId).

Keep ordinary screens in the burrow's language. Offer an optional “How it's built” explanation with these precise technology names and public/private boundaries. Do not imply that every action writes to a blockchain, that all data is decentralised, or that a signed result proves its arithmetic without independent tallying.

## Recommended exploration

1. **Settle the creature art first.** Claude Code should propose and compare silhouettes, facial expression, proportions, palette, framing, and motion at real launcher, onboarding, tutorial, and game sizes. Codex should supply a fixed address/variant gallery, consistent scene framing, and production-parity previews. Do not silently replace the locked identity of existing users while exploring.
2. **Preserve reproducibility before public registration.** Propose per-profile generator version and a versioned manifest covering generator code, canonical parameter encoding, renderer/assets, cryptographic content hashes, and independent fixtures. Retain old versions. A parameter hash preserves parameters; a renderer/assets hash is also needed to identify the intended appearance. A hash alone does not keep its referenced files available.
3. **Anchor the recipe if durable public provenance is wanted.** A project-authored EAS attestation on Base could record a versioned generator/renderer manifest hash and a durable artifact reference. This preserves evidence of the published recipe without publishing anyone's address, critter choice, or burrow membership. EAS supports schemas for structured claims; authenticity and meaning still depend on who attests. [EAS overview](https://docs.attest.org/).
4. **Treat personal identity registration as a separate opt-in decision.** A person could later sign or publish an address-bound version/variant commitment referencing that manifest. Public address/variant data is linkable; hashing this small, guessable input does not make it private. Private commitments require fresh secret randomness and a recovery/disclosure design, and a public transaction still reveals its sender. EAS can attest to a commitment, but an attestation alone does not enforce one current critter per address or an irreversible lock. Those rules would need a defined authority or registry. No NFT is needed for either option. [EAS privacy guidance](https://docs.attest.org/docs/core--concepts/privacy), [EAS private-data attestation mechanism](https://docs.attest.org/docs/tutorials/private-data-attestations).

Keep burrow membership and private scatter choices off public registries. Public result publication remains an explicit feast choice under the existing contract; it must not become a side effect of identity work.

For example, an artifact manifest could identify `generatorVersion`, `generatorHash`, `rendererHash`, `assetsHash`, `parameterEncoding`, and `fixtureHash`; a Base record would publish its canonical `manifestHash` and artifact reference. This is public provenance for an externally executed generator. It does **not** mean the generator or SVG renderer executes onchain. Executing and rendering entirely onchain would need a separate contract/asset design, parity proof for the existing arithmetic, and cost evaluation.

Open choices before implementation: preserve existing v1 identities or invite an explicit migration; define what is permanent (recipe, appearance, or address-bound choice); decide whether users may change or recover identity; choose project-only provenance versus opt-in personal publication; define artifact availability, gas payer, chain/environment, and verification semantics. Workstream A owns persistence and public commitments; workstream B owns art and rendering; profile/version wire changes require shared review. No code, dependency, schema, ADR, transaction, or deployment change was made for this research.
