# Injected account and ENS fixtures

Recorded 2026-09-05 for phase 2 ticket 03. EIP-6963 discovery retains its announcement listener for the page lifetime and dispatches a request after listening; UUID deduplication also handles repeated announcements. Signing uses viem's custom EIP-1193 transport without requesting a chain switch. Result transactions alone request the configured Base chain. Sources: [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963), [viem account client](https://viem.sh/docs/clients/wallet).

`tests/api/fixtures/ens-mainnet.json` contains two actual read-only `eth_call` responses from the public mainnet RPC `https://ethereum-rpc.publicnode.com`, recorded using the pinned viem 2.56.0. They resolve the public address `0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045` to `vitalik.eth` and forward to the same address. The test replays matching method/parameters without fetch. The mismatched-address case deliberately mutates the recorded forward result. No credentials, signatures or transactions were sent. This is a protocol fixture, not a claim that the name will always resolve that way.

The server normalizes names and explicitly checks their forward address before caching a reverse name. Successful positive and negative results use the existing 24-hour database cache. RPC failure returns the address plus `err.ensUnavailable`; it does not overwrite the cache with a successful-looking negative result. Sources: [viem ENS address action](https://viem.sh/docs/ens/actions/getEnsAddress), pinned `viem/actions/ens/getEnsName.ts` and `getEnsAddress.ts`.
